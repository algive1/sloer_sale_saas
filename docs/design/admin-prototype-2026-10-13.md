## 当前后台与设计依据

现有后台由 Saleor Dashboard 提供管理外壳，Commerce Ops 在同源嵌入视图中提供扩展功能。已有两层导航和外壳不应重复出现；本原型用一套侧栏和一条全局工具栏表达完整管理界面。

现有导航顺序为：首页、订单、商品、客户、营销、数据分析、在线商店、销售渠道、应用、设置。原型沿用此顺序，使用缩进、折叠箭头、底色和选中标识明确区分一级分组与二级页面，消除官方 App 扩展与自定义入口重复出现时的视觉干扰。后续实现需核对每个扩展来源，保留其他第三方 Apps 的真实入口与权限。

原生商品、规格、库存、订单、客户、优惠、渠道、员工与权限等功能继续使用 Saleor 现有页面。品牌站点下已有商品发布核对、发货队列、单号回填、上线验收与实时数据；这些保留在品牌详情上下文中，不为展示原型新增独立业务。

七个系统插件依据 `storefront/src/plugins/system/registry.ts`；页面与菜单依据 `dashboard/src/components/Sidebar/menu/commerceOpsNavigation.ts`、`storefront/src/lib/ops/saleor-app-navigation.ts` 及对应 Ops 页面。

| 插件                | 菜单归属与真实页面                                                                            | 现有能力及设计边界                                                                 |
| ------------------- | --------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| `theme-builder`     | 在线商店 → 主题装修 `/ops/themes`；商品详情页模板 `/ops/themes?pageType=product`              | 首页和商品详情模板、草稿与发布、Puck 编辑器；AI 文案与图片属于编辑器内部能力       |
| `analytics`         | 数据分析 → 经营总览 `/ops/analytics`，以及 `realtime`、`traffic`、`checkout`、`products` 子页 | 第一方经营分析与历史报告；不可用、未配置、空数据分别表达                           |
| `ads-tracking`      | 应用 → 广告投递 `/ops/analytics/destinations`                                                 | 品牌接收端配置诊断与投递记录；不是广告活动或预算管理                               |
| `payment-reminders` | 订单 → 智能催付 `/ops/analytics/reminders`                                                    | 品牌规则、人工催付、自动催付、发送记录；邮件、可信订单与调度配置是执行条件         |
| `customer-support`  | 客户 → 会话工作台 `/ops/support`；Chatwoot 设置 `/ops/support/settings`                       | 既有 Chatwoot、WhatsApp 与 AI 客服接入，按实际配置表达状态                         |
| `ai-translations`   | 在线商店 → AI 多语言 `/ops/translations`                                                      | 任务队列、AI 草稿、审核、导出与受限制的发布；不可宣称覆盖所有原生后台译文          |
| `seo-merchant`      | 应用 → SEO 与 Merchant Feed `/ops/merchant`                                                   | Feed 状态及部署配置说明；基础 SEO、sitemap、canonical 与结构化数据继续使用现有实现 |

系统插件在平台统一部署，适用于全部店铺；品牌数据授权与插件可用性是不同边界。官方 App 配置页提供 `/ops/plugins` 状态入口。原型不增加按店铺安装、卸载或启停开关；“代码集成”“系统允许运行”“业务配置完成”“真实验收完成”不能合并成一个绿色成功状态。

## 视觉方案

用户补充约束：“配色 UI 现代一些，不要有 AI 味”。最终方向为浅色导航、灰白表面、深色文字与少量低饱和雾蓝色，依靠排版、对齐与信息层级建立质感。用户的新要求优先于旧分析规范中的深色侧栏视觉要求；经营数据口径与已有功能保持不变。

| 角色     | 原型建议值                   | 用途                           |
| -------- | ---------------------------- | ------------------------------ |
| 导航背景 | `#f6f7f9`                    | 浅色导航、品牌与账号区域       |
| 内容背景 | `#fafbfc`                    | 轻微区分内容与白色模块         |
| 模块     | 白色、细灰边框、5–6px 圆角   | 图表与业务表格，基本不使用阴影 |
| 主强调色 | `#496786`                    | 当前菜单标识、链接和经营曲线   |
| 提示色   | 低饱和绿 / 琥珀色            | 仅用于已付款、待付款和问题提示 |
| 字体     | 现有中文无衬线字体与等宽数字 | 清晰中文、金额和数值列对齐     |

六个 KPI 改成一条开放式指标带，用细分隔线与数值字号建立层级。移除彩色图标底块、渐变、发光、立体标志、大圆角胶囊和装饰性图形。结账健康度使用简洁的文字指标；图例颜色与数据行保持对应，状态同时提供文字。

这些是视觉提案值。后续落地需复用 Macaw UI 组件与令牌、CSS Modules 和现有后台主题机制，不能将图片中的色值直接散落到组件或导入店铺样式。本次参考 `ui-ux-pro-max` 的数据密集后台规范；未采纳与后台不匹配的营销页结构、紫粉配色与夸张字号，也不更换现有组件库。

## 经营总览布局与指标

1. 一条全局搜索与账号工具栏；明确的“设计预览 · 示例数据”标识。
2. 页面标题、平台汇总范围、USD/UTC 口径，7/30/90 天总览范围。
3. 第一行开放式六列指标带：访问会话、成交订单、转化率、净成交额、客单价、弃单结账。
4. 第二行三卡：转化漏斗、流量构成、Top 流量来源。
5. 第三行两卡：经营趋势、结账健康度。
6. 第四行两卡：商品表现、地区与市场。
7. 底部最近订单，保留查看与受配置约束的催付入口。

口径沿用现有功能：漏斗按去重会话统计；转化率使用购买会话除以访问会话；流量环形图只表示渠道流量份额；未知归因保留；不同币种不直接汇总；商品金额标为“已追踪商品金额”；待付款订单没有可靠付款时间时展示“—”；未知运费不填零。

原型中的示例数字用于表现排版，不是从运行数据库读取。没有补造同比环比、通知服务、预测、AI 经营建议、广告活动管理或其他不存在的业务接口。

本次仅交付图片和设计文档。图片无法代替交互原型、真实页面截图或联调证据。当前本机分析服务未配置；支付、广告、邮件、Chatwoot 和 AI 等外部服务是否正常运行，继续以各功能的真实配置和验收为准。

实现后的 UI 应检查：侧栏展开/折叠、当前路由、键盘焦点、深浅主题、中英文、嵌入时内层导航隐藏、375px 窄屏和表格滚动；页面必须区分加载、空数据、配置缺失、存储失败、暂停和权限不足。根据实际代码范围运行 Dashboard 类型/Lint/Jest 与 Storefront `verify`；涉及动态布局再执行构建及相关 E2E。
