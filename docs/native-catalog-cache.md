# 原生商品事件与品牌目录刷新

商品发布、商品/分类/集合修改后，列表和Sitemap需要收到原生事件后刷新。浏览页保留原有缓存，购物车/结账继续实时读取Saleor；缓存刷新不是新的商品数据存储。

## 源码修复

- 已签名事件中的明确市场/市场分配，只匹配本部署配置的市场；明确的外部市场不改用默认市场。原生全局事件省略市场时，刷新所有已配置市场的列表；商品详情保留原有共享商品标签。
- 多品牌以可信品牌注册表的市场集合为准，不用遗漏品牌或包含内部市场的旧全局配置；品牌配置损坏时拒绝处理，不改用全局市场。
- Sitemap缓存纳入统一cache-manifest。清单和游标页使用同一市场标签；商品、分类、集合生命周期或市场启停事件按`{expire: 0}`同步失效，避免清单从仍然陈旧的子页重新生成。
- 规格价格/库存、媒体及元数据事件沿现有展示缓存规则处理，不反复清空Sitemap。手动全量清除包含新的Sitemap配置项。
- Compose在运行时注入`SALEOR_WEBHOOK_SECRET`和`REVALIDATE_SECRET`，均是服务器字段，不能使用NEXT_PUBLIC或构建参数公开。

## 原生配置

在原生员工后台的App详情配置目录Webhook。App至少拥有MANAGE_PRODUCTS；回调为本部署HTTPS地址的`/api/revalidate`，将Webhook的`secretKey`设置为服务器`SALEOR_WEBHOOK_SECRET`的同一随机密钥。当前接收器校验原生HMAC；不设置secretKey时Core默认使用JWS，不能当作已配置HMAC。所有副本应使用一致配置。

按实际用途订阅商品、规格、分类、集合及市场事件，并使用包含实体slug和市场分配的原生订阅查询。分类/集合查询无需伪造市场。可以使用现有转发App或直接原生Webhook这条链路；同一事件应只有一个入口，避免重复投递与刷新。原生系统的正常重试继续保留。

本批不自动配置生产App、真实域名或密钥。`infra/saleor/bootstrap_cache_ci.py`只能在一次性CI数据库运行，不能用于生产。生产仍需配置、投递回执、各副本/共享缓存及规模验收。

## 验证

单元回归包括未授权拒绝、全局事件刷新两个市场、明确市场/外部市场限制、规格事件不重建Sitemap、缓存清单与全量清除。

真实CI先读取并缓存Jewelry Sitemap，确认101规格fixture尚未发布，再从品牌后台打开原生批量向导。发布成功后由Saleor worker产生并签名ProductUpdated；事件故意省略市场，验证非默认Jewelry Sitemap出现新商品，全程不发送手动清除请求。随后检查原生EventDeliveryAttempt的200/成功状态及两个市场的缓存标签。错误签名被拒绝。

验收与合并状态见对应PR。CI证明该一次性环境的原生投递，不代替生产基础设施、完整事件组合或商业上线证据。
