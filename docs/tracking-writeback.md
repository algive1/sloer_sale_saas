# 货代单号回填

入口：个人管理员登录后，品牌“发货与货代交接” → “回填货代物流单号”，地址 `/ops/sites/{siteId}/tracking`。品牌分析员和旧共享 analytics 账号不能读取或提交此功能。

1. 在原生 Saleor 后台完成实物发货。此功能不创建履约、不扣减库存、不调用货代。
2. 选择当前品牌/市场的履约，下载模板。按 `order_id,fulfillment_id,tracking_number` 三列填写，每批1–10笔，UTF-8 CSV最大64KB；一个履约对应一个单号。可先下载空白模板。
3. 上传并预检。当前原生记录必须已付款、订单为已发货/部分发货、履约为 FULFILLED且包含实物。不同订单的履约、取消/退款/退货履约、不同已有单号、重复ID、公式或URL会阻断本批。
4. 核对包裹与单号后确认提交。预检绑定个人、品牌、市场及解析后的文件内容，有效5分钟；提交前全批重读，再逐笔重读。
5. 下载逐笔结果，并查看按品牌/市场保存的最近30条审计。原生回填确认与物流揽收/投递是不同事实。

## 配置与边界

服务器必须明确配置 `OPS_FULFILLMENT_SALEOR_TOKEN`（原生 MANAGE_ORDERS）、可信品牌注册表、个人 `OPS_OPERATORS_JSON` 和可写 `ANALYTICS_LIBSQL_URL/AUTH_TOKEN`。回填不使用全局 `SALEOR_APP_TOKEN` 回退。`SALEOR_DASHBOARD_URL` 用于结果中的原生核对入口。代理应允许此私人API最长180秒；小批顺序提交，每次上游超时5秒。

原生 `orderFulfillmentUpdateTracking` 固定 `notifyCustomer:false`。原生异步履约事件/Webhook仍遵循Saleor配置；此功能没有承诺关闭其他App的事件处理。顾客邮件重试、客服自动通知、承运商跟踪服务仍是后续项目。

运营审计属于核心功能，独立于可选 analytics 采集开关。系统暂停分析采集不应取消交易操作的审计。数据库保存个人账号、品牌/市场、订单/履约ID、单号摘要和状态，不保存原始CSV、地址、明文单号或供应商响应。过期预检在下一次预检时清理。活动回填记录不自动删除，以保留防重和待核对事实；正式数据保留/删除策略须另行验收。

## 失败与人工核对

- 预检失败或全批提交前状态变化：没有发送本批原生回填，修正后重新预检。
- 逐笔原生明确拒绝或写入前读取失败：保留拒绝记录，可在核对后进行新的预检/确认。
- 超时、网络中断、响应不完整或确认后审计写入失败：标记“待核对”，停止后续行；数据库的处理中/待核对占位阻止自动重发。剩余行显示未尝试，不能算完成。
- 用相同CSV重新预检，若原生已存在相同单号，可确认原生事实并修复审计，**不会再次发送回填**。若原生仍为空、或目标单号不同，必须先在原生后台人工核对；此页不提供强制解锁/覆盖。
- 原生API没有 expected-version/CAS参数。提交前的重读不能消除原生后台或其他App在同一瞬间修改的竞争；禁止两边同时处理同一履约。此实现只为本Ops回填建立数据库原子占位，不声称锁定整个Core。
- 批量不是跨原生服务与SQLite的原子事务。部分成功按行呈现，不能把HTTP 200当作所有行成功。

## 发布与验证

新增 `ops_tracking_previews`、`ops_tracking_attempts`，沿用货代导出审计 `ops_shipping_exports`。三个核心运营表在存储契约的 `core.operations` 单独声明，七模块仍各自拥有原17表。恢复检查按存在的核心表校验字段、品牌约束、主键、回填状态和活动占位唯一性；缺失的合法唯一索引报告为运行时待创建，错误索引/重复占位拒绝发布，不修改快照。

本地使用 `scripts/mock-ops-tracking.mjs`（强制loopback及CI专用凭证）与SQLite/Hrana测试后台操作，不能代替原生验收。完整CI用原生 Transactions 已付款订单、库存分配和 `orderFulfill` 创建测试履约，再通过生产构建后台回填、重读原生单号、核对唯一审计和重放；只在显式loopback CI执行，不会向真实货代发运或发送顾客邮件。
